# Fork Infrastructure Setup Guide

## Overview

This document describes the comprehensive automation infrastructure created for forking and maintaining 10 unmaintained Next.js packages under the `@opensourceframework` scope.

## What Was Created

### 1. Automation Scripts

#### `scripts/fork-setup.sh`
Main script for forking a single package.

**Usage:**
```bash
./scripts/fork-setup.sh <package-name> <repo-url> [original-author] [original-package-name]
```

**Example:**
```bash
./scripts/fork-setup.sh next-seo https://github.com/garmeeh/next-seo "Gary Meehan" next-seo
```

**Features:**
- Clones external repository to temp directory
- Transforms package.json to use `@opensourceframework/*` naming
- Updates README with attribution and branding
- Sets up .changeset, TypeScript, vitest, tsup configs
- Creates initial commit with migration note
- Idempotent with `--force` flag

#### `scripts/setup-all-packages.sh`
Orchestration script for setting up all 10 packages in priority order.

**Usage:**
```bash
# Dry run to see what would be done
./scripts/setup-all-packages.sh --dry-run

# Skip packages that already exist
./scripts/setup-all-packages.sh --skip-existing

# Start from specific package index
./scripts/setup-all-packages.sh --start-index 3

# Force overwrite existing packages
./scripts/setup-all-packages.sh --force
```

**Package Order (Priority):**
1. next-compose-plugins (low effort, high impact)
2. next-cookies (low effort, medium impact)
3. next-mdx (low effort, low-medium impact)
4. next-session (medium effort, medium impact)
5. next-iron-session (medium effort, medium impact)
6. next-seo (medium effort, high impact)
7. next-transpile-modules (low-medium effort, high impact)
8. next-auth (very high effort, critical)
9. next-pwa (high effort, high impact)
10. react-virtualized (high effort, high impact)

#### `scripts/security-audit.sh`
Runs security audits on all packages and generates reports.

**Usage:**
```bash
# Audit all packages with low+ severity
./scripts/security-audit.sh

# Audit with moderate+ severity only
./scripts/security-audit.sh --level moderate

# Audit specific packages
./scripts/security-audit.sh --packages next-csrf,next-images

# Audit and attempt to fix
./scripts/security-audit.sh --fix
```

**Output:**
- Markdown report: `plans/security-audits/audit-report-[timestamp].md`
- JSON summary: `plans/security-audits/audit-summary-[timestamp].json`

**CI/CD Integration:**
Fails on critical/high vulnerabilities by default.

## How to Use This Infrastructure

### First Time Setup

1. **Ensure prerequisites:**
   - Node.js 20+
   - pnpm 9+
   - Git with GitHub SSH access configured
   - npm account with access to `@opensourceframework` scope

2. **Reserve package names on npm:**
   ```bash
   # Create placeholder packages to reserve names
   for pkg in next-seo next-transpile-modules ...; do
     # Create minimal package and publish
     # See plans/npm-squatting-monitor.md for details
   done
   ```

3. **Run dry-run to verify:**
   ```bash
   ./scripts/setup-all-packages.sh --dry-run
   ```

### Forking Packages

**Option A: Fork all packages at once**
```bash
./scripts/setup-all-packages.sh
```

**Option B: Fork specific packages**
```bash
./scripts/fork-setup.sh next-seo https://github.com/garmeeh/next-seo "Gary Meehan" next-seo
./scripts/fork-setup.sh next-transpile-modules https://github.com/hoangvvo/next-transpile-modules "Hoang Vo" next-transpile-modules
```

**Option C: Fork from a specific index**
```bash
./scripts/setup-all-packages.sh --start-index 3  # Start at package #4
```

### After Forking

For each forked package:

1. **Review package.json** - Ensure all fields are correct
2. **Update README.md** - Add specific documentation, examples
3. **Add tests** - Import original tests, add new ones
4. **Run build**: `pnpm --filter @opensourceframework/package-name build`
5. **Run tests**: `pnpm --filter @opensourceframework/package-name test`
6. **Create changeset**: `pnpm changeset`
7. **Security audit**: `./scripts/security-audit.sh --packages package-name`
8. **Update CODEOWNERS** if needed (already done for all)

### Ongoing Maintenance

#### Weekly
```bash
# Security audit
./scripts/security-audit.sh --level moderate

# Check npm package name availability (if not yet published)
./scripts/check-npm-names.sh  # Create this from plan in npm-squatting-monitor.md
```

#### Per Release
1. Ensure all tests pass
2. Security audit passes (no critical/high)
3. Changesets created for all changes
4. Version bump: `pnpm changeset version`
5. Build: `pnpm build`
6. Publish: `pnpm changeset publish`

#### Per PR
- All automated checks pass (CI)
- At least one maintainer approval
- For security-critical packages: additional security review
- Changeset included for user-facing changes

## Key Decisions

### Why This Structure?

1. **Automation First**: Scripts handle repetitive tasks (forking, config setup)
2. **Templates**: Ensure consistency across all packages
3. **Placeholders**: Clear status tracking for pending packages
4. **Security Focus**: Dedicated audit script and monitoring
5. **GitHub Integration**: Issue/PR templates tailored for multi-package repo

### Package Naming

- All forked packages use `@opensourceframework/*` scope
- Original attribution preserved in package.json and README
- Clear "maintained fork" messaging

### Security Approach

- Security-critical packages identified (next-auth, sessions, CSRF)
- Weekly automated audits
- Fail builds on critical/high vulnerabilities
- Dedicated security reporting process

### Testing Strategy

- Minimum 80% coverage (100% for security-critical)
- Vitest for unit/integration tests
- TypeScript strict mode
- Type checking in CI

## Next Steps After Setup

1. **Execute forking** using `setup-all-packages.sh`
2. **Reserve npm names** (see npm-squatting-monitor.md)
3. **Complete modernization** per package plan (plans/modernization-plans.md)
4. **Publish packages** after testing and security audit
5. **Monitor** with weekly security audits
6. **Communicate** adoption to users via migration guides
